## 一、清理原则（先读这一章，避免误删）

1. **零调用 ≠ 无用。** 项目仍在推进中，未被前端调用的接口很可能是"进度未到"。**禁止**仅凭"双端无引用"删除接口。
   - 原排查列出过 **40 个**零调用接口作为保留候选，见第四章；这属于历史记录。后续可以在完整保留能力的前提下收敛路由，不能仅据零调用删除。
2. **以功能被完整保留为收敛前提。** 以下情况只能作为重复候选线索，不能单独决定删除：
   - 两个接口调用**同一个 Service 方法**（换了个路由壳）；
   - 两个接口落在**同一条 Mapper SQL** 上；
   - 一个接口的返回是另一个的**严格子集**（投影或条件）。
   - 必须继续核对：输入语义、返回结构、排序、错误行为、授权、业务副作用、查询与签名成本。相同SQL不代表相同API契约。
3. **删除前确认副作用不丢**：审计日志、提审（submitForReview）、邮件通知、COS 对象清理等，这些常常只挂在被删的那条链路上。
4. **删除前确认鉴权不降级、不误拒绝合法调用者**：依据业务权限矩阵处理，不能机械放宽到两侧调用者并集。响应字段或数据范围不同的入口保留授权/投影边界；读取接口合并不改变绑定、指派、审核等写权限。
5. 前端同步：API 封装壳（`workManage.ts` 之类）也要一并清掉，否则留下指向 404 的死函数。

## 三、批次 2 实施细节（会话中断后照此继续）

### 2-1 `POST /api/work/works_by_username`

- **重复证据**：`WorkController.java` 中该方法的 `username` 形参**已被注释掉**，方法体直接调 `workService.getWorkByPageService(statusEnum, pageRequestDto)` —— 与 `POST /api/work/works_by_page` 完全同构。
- **性质**：这是"名字承诺按作者查、实际不按作者查"的**假接口**，不属于"进度未到"，保留只会误导后续开发。
- **删法**：删 `WorkController` 的方法 + 前端 `BarcFrontend/src/stores/AccountWorkItemListPinia.ts` 里那行已注释的旧调用残留。

### 2-2 `GET /user/permission/permission_near_max`

- **重复证据**：`UserPermissionController` 的两条路由调**同一个** `getUserPermissionNearMaxService`。
- **保留方**：`GET /user/permission/me_permission_near_max`（从 token 取 uuid，只查自己）。
- **注意**：被删的那条是 `@IgnoreAuth`（任何人可查任意 uuid 的权限文案）；保留方走 token，鉴权更严但不影响其调用者（前端只在登录后调用）。

### 2-3 `GET /comment/message_board/all`

- **重复证据**：与 `GET /comment/message_board/new?limit=` 同表，投影同为 `MessageBoardModel` 全字段；`new` 传大 limit 即可达全量。
- **注意**：`selectAll` 无排序也无条数上限；删除后要在 `new` 的 `selectByLimit` 上补注释说明"全量 = 传大 limit"，否则后人找不到全量入口。

### 2-4 `PUT /api/work/manage/update` —— ⏸️ 2026-10-12 复核后判定：**不属重复，不删**

- **原重复判据**：与 `PUT /api/work/edit-update` 落到**同一条 SQL** `workMapper.updateText`（`WorkMapper.java:153-156`）。
- **执行前复核推翻了该判据** —— 两者除了共用底层 SQL，其余全不相同：

  | 维度 | `PUT /api/work/manage/update`（管理端） | `PUT /api/work/edit-update`（作者侧） |
  |---|---|---|
  | 调用者 | 管理员（`SEC_MAINTAINER` 位） | 作品作者 / 收录者本人（`isWorkOwner` 校验） |
  | 能否改他人作品 | **能**（无归属校验，可改任意作品） | **不能**（非本人直接拒绝） |
  | 副作用 | `recordLog(OP_EDIT)` 操作日志 | `submitForReview` 重新提审 |
  | 前端调用 | `workManage.ts` 有封装壳，**无组件调用** | `ManageWorkEditComp.vue` 真实调用 |

- **结论**：这是"两个角色各自的内容编辑入口共用一个底层 UPDATE"，属**合理的分层复用**，不是重复造轮子。按第一章原则 1（零调用 ≠ 无用），它属于"管理端编辑作品的界面尚未开发"的预留接口。
- **删除的后果（复核修正）**：会失去这条明确带操作日志的管理编辑链路。旧 `/api/work/update` 仍能供二级管理员全字段更新，但缺少同样的边界和审计，是需修复/收敛的旧入口，不能当作安全等价替代；不能断言管理员将“永久失去全部编辑能力”。
- **后续可选改进（本次未执行）**：作者侧编辑目前**没有操作日志**，管理端操作日志页看不到作者改了什么。若要补，需在 `WorkService` 注入 `WorkOperationLogMapper` 并复刻 `WorkManageService.recordLog`（`WorkManageService.java:465-475`）。这是独立的可观测性改进，与重复清理无关，需单独授权。

### 2-5 认领两条

- **重复证据**：`WorkClaimService` 的两个方法分别与 `WorkManageService.getClaimsList` / `getClaimHistory` 调**同一个 Mapper 方法**（`workClaimMapper.selectAll()` / `selectByWorkId(workId)`）。
- **保留方**：管理端两条（返回 `WorkClaimListDto`，是字段超集）。
- **必须做的前置改造**：管理端两条当前是 `SEC_MAINTAINER` 位（1匹配）。用户端两条是手写的"MANAGER 身份 + 风纪委员位"。删除用户端后，**风纪委员将无法查看认领申请**。
  - 改法：把两个方法的注解改为
    `targetPermission = PermissionConst.SEC_MAINTAINER | PermissionConst.DISCIPLINARY_COMMITTEE`。
  - **原理**：`ComparePermission.has(your, target)` 是 `(your & target) != 0`，因此 target 传"多个位的或"天然就是 **OR 语义**（持有 4 或持有 1 都通过）。
  - 保持 `identity = MANAGER` 不变（风纪委员与管理员同属 MANAGER 身份），`isHasElseUpper = true`、`isSuchElseRequire = false`。
- **不要动**：`WorkClaimController` 的 `/claim_check` 与 `/upload`（认领功能的提交与审核入口，**用户明确要求保留**）；`WorkClaimService.getClaimsByUuidControl` 虽无 Controller 入口，但属"进度未到"，保留。
