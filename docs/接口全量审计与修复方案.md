## 一、我的判断与处理原则

当前最紧迫的问题是授权、账号验证和数据完整性，接口数量本身不是首要指标。原 DSH 报告的 179 → 172 → 167 计数与已执行清理基本属实，但没有覆盖这里发现的高风险链路。把“调用同一个 SQL/Service”当成删除接口的充分依据不成立。

本文整理 **40 组问题与改进项：6 组 P0、23 组 P1、11 组 P2**。它们按根因归组，并不表示恰好40条有问题的接口。一个根因可能影响多个入口，部分条目是契约完善或安全加固项。每组均列出现象、证据、建议、受影响功能、改动风险和验收条件。

- **P0**：应先阻断的越权、账号安全或脚本注入链路。
- **P1**：严重业务缺陷、数据损坏风险或重要安全边界问题。
- **P2**：可用性、契约、性能、维护和验证体系问题。
- **改动风险**指修复引入回归的风险，与当前缺陷严重程度不同；没有真实统计依据，不编造风险百分比。
- “已复现”指本地真实方法/切面/SQL构造配合模拟依赖验证；不等同于在真实数据库、浏览器或生产环境中复现。
- “源码确认”有可追踪的控制流/SQL证据；部署配置、存量数据和真正并发行为的待核内容在后文单列。

执行原则：

1. 保留未登录搜索用户和查看公开主页的能力；收敛返回字段，不能一刀切加登录。
2. 保留作品认领；没有前端调用不能作为删除理由。
3. 作者、收录者、管理员各自的授权、提审、审计和通知语义分别保留。
4. 使用数据库对象归属和服务器身份作授权依据；请求体中的 author/permission 不是可信授权数据。
5. 先修业务调用层，保持 COS client 兼容；不改密钥、不直接删除用户数据、不清生产库。
6. 不为减少接口数量牺牲性能或功能。只有契约、授权、副作用和调用方都明确后，才退役兼容入口。

### I01 · 账号权限写入缺少字段和取值边界（P0）

**证据等级：**已复现（P04、P24）。源码：[UserService.java:135](../BarcBackend/src/main/java/com/miaoyu/barc/user/service/UserService.java#L135)；[UserArchiveMapper.java:113](../BarcBackend/src/main/java/com/miaoyu/barc/user/mapper/UserArchiveMapper.java#L113)；[UserPermissionService.java:62](../BarcBackend/src/main/java/com/miaoyu/barc/user/service/UserPermissionService.java#L62)；[ComparePermission.java:18](../BarcBackend/src/main/java/com/miaoyu/barc/permission/ComparePermission.java#L18)。

POST /user/edit_archive 只校验 uuid 是本人，却把客户端 permission 交给通用 UPDATE。已有 MANAGER 账号可自行提高管理权限；普通 USER 可自行改变会员角色位。identity 不在该 UPDATE 中，因此不能把它描述成“普通用户直接改成 MANAGER”。

专用 POST /user/permission/change_permission 也没有校验合法权限位。三级管理员可以给普通目标账号设置 MANAGER/-1：负值通过大小限制，却能命中包括馆长位在内的所有“1匹配”检查。该路径已通过真实切面和服务方法、模拟持久化验证；不等于负值也能通过所有“比大小”检查。

- **我的做法：**个人资料使用字段白名单 DTO，只允许昵称、头像及允许公开的资料；permission、identity、updated_at 均由服务端控制。权限变更只走专门管理接口，按身份校验合法权限位、拒绝负数和未知位，再检查操作者可授予的角色范围，并记录操作者与变更前后值。
- **改动风险：**低：合法个人资料编辑无需改业务含义；旧客户端提交多余字段时忽略或明确拒绝。
- **影响功能：**两端个人资料、权限管理；需排查既有异常权限记录，排查不等于自动修改历史账号。
- **验收重点：**USER、各 MANAGER 位和组合位均不能通过个人资料改变权限；负数和未知权限位在专用入口被拒，不能越级授予管理角色；正常改昵称和合法授权仍成功。

### I02 · 公告更新信任请求体中的作者，可修改他人公告（P0）

**证据等级：**已复现（P01）。源码：[NoticeController.java:72](../BarcBackend/src/main/java/com/miaoyu/barc/notice/controller/NoticeController.java#L72)；[NoticeService.java:103](../BarcBackend/src/main/java/com/miaoyu/barc/notice/service/NoticeService.java#L103)；[NoticeMapper.xml:55](../BarcBackend/src/main/resources/mappers/Notice/NoticeMapper.xml#L55)。

### I03 · 作品删除缺少归属和角色检查，并直接删除文件（P0）

**证据等级：**已复现（P02）；真实存储未操作。源码：[WorkController.java:253](../BarcBackend/src/main/java/com/miaoyu/barc/api/work/controller/WorkController.java#L253)；[WorkService.java:552](../BarcBackend/src/main/java/com/miaoyu/barc/api/work/service/WorkService.java#L552)；[schema.sql:135](../BarcBackend/src/main/resources/schema.sql#L135)。

DELETE /api/work/delete 只检查作品存在，未传入操作者 uuid。Service 直接删除图片、封面和作品，任意有效登录令牌可到达他人作品的删除逻辑。删除中途失败会留下不一致结果；仓库的 work_view_log 外键还可能使最后的作品删除失败，而文件已被删除。

- **我的做法：**立即补上从令牌到对象归属的检查；普通用户删除采用可恢复状态，管理员删除复用带审计的状态服务。物理清理由独立、带引用核查的任务完成，不在请求内同步删 COS。
- **改动风险：**中：删除语义由物理删除收敛为逻辑删除，需统一列表过滤和恢复行为；存量外部调用须兼容。
- **影响功能：**作品详情、作者内容管理、管理端删除/恢复、评论/点赞/浏览记录及图片。
- **验收重点：**非本人拒绝且无任何副作用；作者和授权管理员按规则删除；模拟任一步失败、存在浏览记录时保持数据完整。

### I05 · Naigos 首次登录创建可预测的本地密码（P0）

**证据等级：**源码确认。源码：[SignService.java:94](../BarcBackend/src/main/java/com/miaoyu/barc/user/service/SignService.java#L94)；[SignService.java:102](../BarcBackend/src/main/java/com/miaoyu/barc/user/service/SignService.java#L102)；[SignService.java:41](../BarcBackend/src/main/java/com/miaoyu/barc/user/service/SignService.java#L41)。

Naigos 首次映射账号时设置固定弱默认密码，普通本地登录接口又允许这些账号按该密码登录。外部身份登录创建的账号由此获得不安全的本地登录凭据。

- **我的做法：**新映射账号默认禁止密码登录，或生成不可使用的随机凭据；完成可信邮箱验证后才允许设置本地密码。对历史这类账号制定定向迁移方案，并使旧会话按需要失效。
- **改动风险：**高：涉及既有账号与登录体验；必须先识别受影响账号，避免把已主动设置密码的人一起锁出。
- **影响功能：**Naigos 登录、本地登录、找回/设置密码、既有账号迁移。
- **验收重点：**新外部账号不能用固定默认密码登录；已绑定并设置密码的正常账号不受误伤；中途失败不产生半个账号。

## 三、原重复接口清单的处理结论

用户检索与相似接口的完整对照已单列为[重复接口专项复核](重复接口专项复核.md)，含21组比较、修复风险和功能影响。特别区分：用户无条件/带条件分页SQL已在`9304d4f`合并；两条用户选择器搜索仍待收敛。另纠正旧台账：通用作品分页已经支持学园/部团/学生的精确ID筛选。

| 对象 | 复核结论 | 我的决定 | 改动风险与影响 |
|---|---|---|---|
| 作者/管理端 `edit-detail` | DTO组装重复，授权边界不同 | 保留两条API，提取共享组装逻辑 | 低；保持响应结构、图片顺序与签名时效，影响两端编辑页 |
| 作品管理/官方账号的用户搜索 | 共享SQL，但权限、空白/空关键词处理不同 | 最终统一通用轻量搜索；旧入口先兼容委托，迁移后退役；绑定/指派写权限保留 | 低至中；影响指派作者、官方账号选择，先修I17返回类型问题 |
| 作品按学园/部团/学生查询与通用分页 | 通用分页已支持对应精确ID；旧数组/全字段投影与新分页卡片不同 | 共享查询核心，统一字段及分页契约后收敛路由，保留筛选能力 | 中；同时修部团JOIN和封面签名，详见专项D03 |
| 分类作品分页与一般作品分页 | 分页包装/投影/签名重复，但keyword匹配范围不同 | 通用查询增加category_id，统一搜索语义后迁移旧入口 | 中；影响分类浏览、作者昵称检索与总数，详见专项D05 |

| `manage/update`、`edit-update`、旧 `work/update` | 管理编辑、作者提审、旧全量更新副作用不同 | 保留明确业务入口；旧入口委托到受控服务，见I27 | 中；涉及归属、提审与审计，不能简单删路由 |
| 两处认领审核 | 确实存在重复业务实现，但角色和副作用不一致 | 共享审核命令，旧入口兼容委托；认领能力完整保留 | 中至高；见I17、I18、I29 |
