> **适用对象**：未来负责「邮箱发送功能大修」的 Agent 或开发者。
> **登记日期**：2026-10-10
> **登记时状态**：邮箱链路**未做任何改动**。同日只修复了 `basic_me` 脱敏与作品认领越权两处（提交 `3ce9f15`），与本文档无关。

## 一、为什么单独立档

注册与找回密码都依赖邮箱验证码。这条链路目前**能用**，但缺少一切防滥用手段，属于"功能正确、健壮性欠账"。它的改造会同时牵动：

- 后端接口鉴权与限流；
- 前端两个调用点（用户前端的注册页、找回密码页）；
- SMTP 同步发信慢（12~13 秒）与前端超时之间的历史妥协；
- 验证码表 `verification_code` 的结构与生命周期。

这四件事互相牵连，**不适合顺手改**。所以先把现状与坑记全，等大修时一次性处理。

## 二、当前链路事实

### 2.1 接口清单与鉴权

| 接口 | 位置 | 鉴权实际状态 |
|---|---|---|
| `GET /email/send/signup?email=` | `SendEmailController#sendSignupEmailControl` | **完全公开** |
| `GET /email/send/reset_password?email=` | `SendEmailController#sendResetPasswordEmailControl` | **完全公开** |
| `GET /email` | `HelloWorldController#sendTestEmail` | **完全公开**，测试残留 |

**"完全公开"的成因（重要，容易误判）**：`AuthInterceptor` 只拦截 `WebConfig` 中登记的路径前缀 —— `/hello/**`、`/user/**`、`/api/**`、`/comment/**`、`/feedback/**`、`/trend/**`、`/notice/**`。**`/email/**` 不在其中**，所以这两个接口既没有 `@IgnoreAuth`、也没有登录门槛，属于"绕过了拦截器"而不是"显式公开"。看注解会以为它们需要登录，实际不需要。

### 2.2 发码与校验流程

**注册发码** `SendEmailService#sendSignupEmailService`：

1. 生成 6 位数字码；
2. 写入 `verification_code`，有效期 **30 分钟**，`scenario = "Signup"`，`username` 存邮箱；
3. 作废该邮箱此前未使用的注册码（`invalidatePreviousSignupCodes`，按 `unique_id` 精确作废）；
4. **异步**发信；
5. 立即返回 `unique_id`。

**重置密码发码** `SendEmailService#sendResetPasswordEmailService`：

1. 先按邮箱查 `user_basic`，**查不到直接返回 `noSuchUser`**；
2. 生成 6 位数字码，有效期 **5 分钟**，`scenario = "ResetPassword"`；
3. **不作废旧码**（与注册不一致）；
4. 异步发信，立即返回 `unique_id`。

**校验** `SignService#checkSignupCode`：按 `unique_id` 取记录 → 校验邮箱/场景/是否已用 → 比对码 → 校验是否过期 → 标记已用。**全程没有尝试次数计数，也没有失败锁定。**

### 2.3 异步发信（历史妥协，必须保留）

`MailDispatcher` 是**独立 Bean**，两个方法标注 `@Async(AsyncConfig.MAIL_TASK_EXECUTOR)`。独立成 Bean 不是风格偏好：`@Async` 依赖 Spring 代理，同 Bean 内部自调用不走代理、等于同步执行。

线程池配置（`AsyncConfig#mailTaskExecutor`）：核心 2 / 最大 4 / 队列 200 / `CallerRunsPolicy`（队列满时由调用线程兜底，宁可慢也不丢信）/ 关闭时最多等 30 秒。

**这个设计的由来**：SMTP 同步发信实测 12~13 秒，超过前端 axios 默认 10 秒超时，会导致"邮件已发出、前端拿不到 `unique_id`"，注册链路整体失败。前端为此专门准备了 `slowHttp`（`SLOW_TIMEOUT = 60000`）。

> ⚠️ **改造时不要退回同步发信**，除非同时把发信耗时压到前端超时以内。

## 三、已知缺陷清单（按风险从高到低）

### 缺陷 1：无任何频控，可被用作邮件轰炸器

两个发码接口都可用 `GET` 直接请求，**没有**同邮箱冷却、**没有**同 IP 限流、**没有**人机校验。任何人（含未登录）都可以对任意邮箱无限发码。

后果：骚扰第三方邮箱、消耗 SMTP 配额、触发邮件服务商风控甚至封禁发信域名。`GET` 语义还会让它更容易被预取器、爬虫或富文本里的图片标签意外触发。

### 缺陷 2：可枚举"某邮箱是否注册过本站"

`sendResetPasswordEmailService` 先查 `user_basic`，查不到返回 `noSuchUser`。攻击者可批量探测邮箱注册状态。注册发码接口则**不查重**，两个接口的行为还不一致。

### 缺陷 3：验证码可被暴力枚举

`checkSignupCode` 没有失败计数与锁定。6 位数字码，重置密码场景有效期 5 分钟，配合缺陷 1 的无限发码，有效期内可高速尝试。**其中"重置密码"场景可直接导致账号被接管**，是本文档里唯一的高危项。

### 缺陷 4：测试残留接口 `GET /email`

`HelloWorldController#sendTestEmail` 硬编码收件人 `1260352143@qq.com`，公开可调，与业务发信无关。连同该 Controller 的 `/hello`、`/hello/test_permission_anno` 一并属于测试残留（`/hello/**` 反而被拦截器覆盖，需登录）。

### 缺陷 5：重置密码场景不作废旧码

注册链路会作废该邮箱的旧码，重置密码链路不会。旧码在 5 分钟内仍然有效，与"新码发出后旧码应失效"的直觉不符。

### 缺陷 6：校验顺序不规范（低危）

`checkSignupCode` 先比对码、后判断是否过期。当前无实质危害，但让"过期"与"不匹配"的错误归因变得不直观。

## 四、改造时不可破坏的契约

这些是双端已经依赖的，改了会直接打断注册/找回密码：

1. **返回结构**：`code = 0` 且 `data` 为本次验证码的 `unique_id`。前端要拿它去调 `/user/sign/up` 或 `/user/reset_password`。
2. **`unique_id` 必须与码同时落库并先于发信返回**。不能改成"发信成功才返回"。
3. **前端调用点**（三处，均用 `slowHttp`，超时 60 秒）：
   - `BarcFrontend/src/components/Sign/SignSignupComp.vue`（注册）
   - `BarcFrontend/src/components/Update/UpdateAccountComp.vue`（找回密码）
   - `BarcFrontend/src/components/Update/UpdateAccountPasswordComp.vue`（找回密码）
   - 封装：`BarcFrontend/src/utils/https.ts` 的 `slowHttp`
4. **两个前端都只调用户前端的这四处**，管理端 V2 不涉及邮箱发码（管理端没有注册/找回密码入口）。

## 五、建议的改造方向

留给大修时取舍，这里只列方向与理由：

1. **把 `/email/**` 纳入 `AuthInterceptor` 覆盖**，再给两个发码接口显式标 `@IgnoreAuth`。这样"公开"变成显式声明，而不是"没被拦截器覆盖"的副作用；测试残留接口则自动回到需要登录的状态。
2. **加频控**：同邮箱冷却（如 60 秒）+ 同 IP 时间窗限流（如 10 次/小时）。落点可以是一张限流表，也可以是 Redis——项目当前没有 Redis，若引入需评估运维成本。
3. **加入人机校验**（图形验证码或第三方），或统一改成 `POST` + 请求体，避免 `GET` 被意外触发。
4. **给验证码校验加失败上限**：同一 `unique_id` 连续失败 N 次即作废，或在记录上增加 `attempt_count` 列（需要迁移脚本，见 `src/main/resources/db/migration/`，当前已到 `V13`）。
5. **统一注册与重置密码的行为**：要么都作废旧码，要么都不作废；并统一"邮箱不存在"的响应语义，堵住枚举面。
6. **顺手清掉 `HelloWorldController`** 的三个测试接口。

> 数据库结构变更请遵循项目既有方式：在 `src/main/resources/db/migration/` 追加新的 `V{n}__xxx.sql`，**不要**改 `schema.sql`（该文件项目已声明退役且与真实库不一致），也不要直接改库。
