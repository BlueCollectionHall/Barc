## 一、先回答用户检索的两类重复

### 1. 原“无条件分页”和“有条件分页”：已经合并

对应的HTTP入口一直是 `POST /user/query/all_by_page`。旧实现根据params是否为空，分别走 `selectByPage` 与 `selectUserInfoByPage`，实际维护了两套用户列表SQL，且投影字段不一致。前序提交 `9304d4f0895da48ab8fbd83696fbd2b9107171cb` 已删除旧分支，当前由一条动态SQL兼容空条件和带条件分页。

所以，当前不能把这一组列为“仍有两个全量用户HTTP接口”。这里的“全量”指不限制筛选条件、可分页遍历全部用户，不是一次请求无限返回全部账号。公开检索能力应继续保留。

本轮重新运行 `UserArchiveMapperUserPageSqlTest` 和 `UserServiceGetUsersByPageTest`，共8项通过；确认空条件、有条件与null参数走统一实现。

### 2. 两条用户选择器搜索：审计时仍重复，现已统一实现

| 比较项 | `/api/work/manage/search-user` | `/user/official/search_user` |
|---|---|---|
| 用途 | 认领管理中指派作者的账号选择器 | 官方账号绑定选择器 |
| 数据查询 | `UserArchiveMapper.searchByKeyword` | 同一Mapper方法 |
| 检索规则 | UUID/用户名/昵称OR，最多15条 | 相同 |
| 实际投影 | uuid、nickname、avatar、username | 相同 |
| 当前授权 | MANAGER且permission≥1 | MANAGER且持有馆长位32 |
| 空关键词 | 未trim，空串会成为LIKE '%%'，取至多15个账号 | trim；空白直接返回空列表 |
| 当前消费者 | `ClaimsListView.vue` | `OfficialAccountsView.vue` |

**最终决定及实施：收敛到通用轻量用户搜索 `GET /user/query/search`。** 下表比较的是审计基线；新入口现已实现并迁移两个选择器，旧入口兼容委托同一服务，待下一次不兼容版本评审再决定退役。

具体规则：统一关键词trim、空白返回空列表、匹配字段、稳定排序、数量上限及最小DTO。查询只返回公开选择字段，按既定的匿名用户检索规则开放；官方账号绑定仍检查馆长位，作者指派仍检查其独立管理权限。不能因为合并读取就放宽写入权限。

先让两条旧接口委托共同查询，再迁移两个选择器，明确兼容期后退役旧接口。既有 `all_by_page` 保留完整分页/筛选能力：它目前是多个条件的组合筛选，不具备同样的一个keyword跨UUID/用户名/昵称OR语义，响应也有分页包装。因此先共享底层用户查询能力，不能不改契约就把两个数组搜索请求硬接过去。

## 二、需要纠正旧台账的一处判断

旧[清理台账](重复接口清理.md)曾把 `works_by_school`、`works_by_club`、`works_by_student` 认定为通用分页覆盖不到的独立查询维度。这不符合当前源码。

`WorkMapper.xml` 的 `whereConditions` 已支持 `school_id`、`club_id`、`student_id`、`author_uuid`、`uploader_uuid`，取数与计数都引用这一条件片段。本轮通过真实MyBatis BoundSql，对这5个字段分别检查取数/计数，10项全部通过，未执行SQL或连接数据库。

这些旧入口与通用分页确有检索能力重叠；保留它们的现实障碍是旧数组/全字段实体与新分页卡片的返回契约、排序和封面签名不同。我的方案是统一查询核心与投影规则后迁移，保留筛选能力，逐步退役重复路由。不能继续用“通用分页不支持这些条件”作为永久保留理由。

## 四、实施取舍

1. **先合并明显重复的业务实现**：通用用户选择器查询、作品编辑DTO构造、认领审核命令、公开作品筛选和分页组装。既有用户分页SQL不重做。
2. **再迁移可收敛路由**：两处用户搜索、作品维度查询、分类分页、旧作品全量/通用更新、动态all/new。每一项先对齐字段、排序、分页、权限及副作用，再迁移双端；兼容期限明确后退役旧入口。
3. **保留有实际边界的变体**：本人/公开/管理查询、轻量选项与带统计列表、动态或作品聚合、不同对象的创建/删除。共享内部实现即可，不为少几个URL让简单查询变重或削弱授权。
4. **不直接放宽到权限并集**：先确认统一响应对哪些角色可见。如果两边数据范围不同，保留投影和授权边界；读操作合并不能改变写操作权限。
5. **删除依据是能力被完整保留**：包括输入语义、输出结构、排序、错误行为、授权、副作用与性能边界。前端零调用仅用于评估迁移成本，不是删除理由。
