# Barc 数据库环境与初始化指南

> 本文档说明开发/生产数据库的环境切换机制，以及新环境（尤其是新生产库）的正确初始化方式。
> 配套脚本位于 `BarcBackend/db/baseline/`。

---

## 一、环境自动切换（已实现）

后端启动时会根据**代码的加载方式**自动选择 Spring Profile：

| 启动方式 | Profile | 数据源 |
|---|---|---|
| IDEA 运行、直接运行 `main`、`./mvnw spring-boot:run` | `dev` | `application.yaml` 中的开发库 |
| 打包后 `java -jar` | `prod` | `application-prod.yaml` 覆盖为 `127.0.0.1:51001/ba-prod` |

判定依据是启动类资源地址的协议：`jar:` → `prod`，其余（`file:`）→ `dev`；无法识别时安全回退 `dev`。

### 1.1 显式覆盖

命令行、JVM 系统属性与环境变量中的显式配置优先于自动识别：

```bash
java -jar BarcBackend-0.1.16.jar --spring.profiles.active=dev
java -Dspring.profiles.active=dev -jar BarcBackend-0.1.16.jar
SPRING_PROFILES_ACTIVE=dev java -jar BarcBackend-0.1.16.jar
```

> ⚠️ 禁止在生产服务器上传入 `dev`，否则服务会主动连接开发数据库。

### 1.2 启动前安全校验（fail-safe）

生产 Profile 激活时，程序会在创建任何数据库连接**之前**校验以下条件，任一不满足即抛出异常并终止启动：

1. `application-prod.yaml` 必须真实存在于运行时的 classpath / JAR 中；
2. 最终生效的 `spring.datasource.url` 必须以 `jdbc:mysql://127.0.0.1:51001/ba-prod` 开头——**同时锁定主机、端口与库名**；
3. `dev` 与 `prod` 不得同时激活。

因此**不会**出现"生产环境静默连到开发库"或"同时连两个库"的情况。

注意两点：
- 必须写成字面量 `127.0.0.1`，写 `localhost` 会被拒绝；
- **开发库与生产库位于同一 MySQL 实例、同一端口，仅库名不同（`ba` 与 `ba-prod`）**，所以校验必须包含库名才能拦住"生产误连开发库"；
- 校验只保证"指向约定的生产库"（本机 51001 端口、库名 `ba-prod`），不保证该库已存在、凭据正确或 MySQL 正在运行——这些仍会以连接失败的形式导致启动失败。

### 1.3 凭据管理

`application-prod.yaml` 优先读取服务器环境变量，未设置时才回退到 `application.yaml` 中的本地值：

```yaml
spring:
  datasource:
    url: jdbc:mysql://127.0.0.1:51001/ba-prod
    username: ${BARC_PROD_DB_USERNAME:${barc.datasource.production.username}}
    password: ${BARC_PROD_DB_PASSWORD:${barc.datasource.production.password}}
```

推荐在服务器设置 `BARC_PROD_DB_USERNAME` / `BARC_PROD_DB_PASSWORD`，这样明文凭据无需写入文件。

> ⚠️ `application.yaml` 与 `application-prod.yaml` 均已被 `.gitignore` 忽略，但 Maven 会把它们原样复制进 `BOOT-INF/classes/`。因此**JAR 内含明文凭据**，必须限制制品、备份与传输渠道的访问权限。

## 二、为什么新库不能直接启动

当前 Flyway 迁移链**无法从空库独立建库**，原因已逐个核对：

| 迁移 | 语句 | 对空库或仅导入 `schema.sql` 的库 |
|---|---|---|
| V1 | `ALTER TABLE schools / students ...` | ❌ 已弃用的复数表不存在，直接失败 |
| V1 | `ALTER TABLE club ...` | 单数 `club` 存在，可成功 |
| V6 | `ALTER TABLE work ADD content_updated_at` | ❌ `schema.sql` 已含此列 → 重复加列失败 |
| V9 | `ALTER TABLE background_image ADD time_period, festival` | ❌ `schema.sql` 已含这两列 → 重复加列失败 |
| V2 | `ALTER TABLE school / student ADD deleted_at` | `schema.sql` 缺失此列，本应成功 |
| V3 | `ALTER TABLE user_basic ADD safe_level_before_ban` + 建 `user_ban_record` | `schema.sql` 缺失，本应成功 |

另外两个必须知道的事实：

1. **执行顺序是 Flyway 先、`schema.sql` 后。** 实测字节码证据：`SqlInitializationAutoConfiguration` 通过 `@Import` 引入 `DatabaseInitializationDependencyConfigurer`，且存在 `FlywayMigrationInitializerDatabaseInitializerDetector`，它让脚本初始化器依赖 Flyway 的迁移初始化器。所以不能指望"`schema.sql` 先把表建好，再跑迁移"。
2. **MySQL 8 不支持 `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`**（这是 MariaDB 语法），因此无法把"加列"迁移写成幂等；基线与后续迁移必须严格互补。

结论：**`schema.sql` 不是最新结构的等价快照**——它超前包含了 V6/V9 的产物，却缺失 V1/V3 的产物。

## 三、`schema.sql` 退役影响面分析（已于 0.1.16 执行）

### 3.1 退役前的职责

退役前，`schema.sql` 由 `spring.sql.init.mode: always` 在每次启动时执行（`CREATE TABLE IF NOT EXISTS`，幂等）。

自 **0.1.16** 起该配置已改为 `never`，文件不再参与启动建表，结构变更全部由 Flyway 迁移承担。

- `schema.sql` 中实际执行的建表语句：**30 张**
- 其中被 `#` 注释、不会执行的：3 张（`schools`、`school_clubs`、`students`，早期复数形态）
- Flyway 迁移创建的：7 张（`cos_garbage_key`、`user_ban_record`、`work_like`、`work_view_log`、`work_review`、`background_image`、`festival`）
- 两者重叠的：5 张（`work_like`、`work_view_log`、`work_review`、`background_image`、`festival`）
- **仅由 `schema.sql` 创建、Flyway 从未创建的：25 张基础表**，包括 `user_basic`、`user_archive`、`work`、`category`、`school`、`club`、`school_club`、`student`、`work_category`、`work_comment`、`work_image`、`notice`、`feedback` 系列等。
- **仅由 Flyway 创建的：2 张**（`cos_garbage_key`、`user_ban_record`）。

列级增量（由 Flyway 添加、`schema.sql` 中缺失或已超前的）：

| 列 | 来源 | `schema.sql` 现状 |
|---|---|---|
| `school.deleted_at`、`student.deleted_at` | V2 | 缺失 |
| `user_basic.safe_level_before_ban` | V3 | 缺失 |
| `work.content_updated_at` | V6 | 已包含（超前） |
| `background_image.time_period`、`background_image.festival` | V9 | 已包含（超前） |

> 真实结构以 mapper 的 `FROM xxx` 为准：当前全部使用单数 `student` / `school` / `club`，与 `AGENTS.md` 的约定一致；历史设计文档中提到的复数表是已被取代的早期形态。

### 3.2 退役后的影响

| 影响对象 | 影响 | 说明 |
|---|---|---|
| 已有环境（开发库、初始化后的生产库） | **无影响** | 全部表已存在，`schema.sql` 原本每次都是空转 |
| 全新环境 | **必须改用 baseline 脚本** | 不能再依赖 `schema.sql` 自动建那 25 张基础表 |
| 缺表的异常环境 | 行为改变 | 原先启动时会静默补建缺失的表，退役后不再补，会变成运行时错误 |
| `AGENTS.md` 约定 | **不冲突** | 该文件禁止"删除 `schema.sql` 中的表"；退役只是不再执行，DDL 定义保持不动 |

### 3.3 退役时的两个注意点（均已处理）

1. **配置无法通过 Git 同步。** `spring.sql.init.mode` 位于 `application.yaml`，而该文件被 `.gitignore` 忽略。已在本机 `application.yaml` 中设为 `never`；由于该文件会被打包进 JAR 的 `BOOT-INF/classes/`，生产环境随新 JAR 一并生效。但**重建该配置或更换环境时必须手工确认为 `never`**，否则新环境又会退回依赖 `schema.sql`。
2. **文档同步（已完成）。** `docs/AI开发指南.md` 的「新增数据库表」与「Q5 字段变更」已改为指引新增 Flyway 迁移，禁忌表也补充了"不要修改已应用到环境的迁移"这条纪律。

## 四、路径 A：用 baseline 脚本初始化新环境（推荐）

零迁移改动、零 history 手术、当天可用。

### 4.1 方式一：全程在服务器完成（推荐）

适用于服务器已装 MySQL 客户端、且能访问源库（开发库）的情况。整个过程只用一台机器，无需中转文件。

**第 1 步：把脚本放到服务器**

任选一种：
- 用 Xftp 上传 `BarcBackend/db/baseline/` 下的两个 `.sh` 脚本；
- 或在服务器用 `vi` 新建文件并粘贴脚本内容。

> 从 Windows 粘贴可能引入 CRLF 行尾（会让 bash 报 `bad interpreter`，或让变量值末尾多出 `\r`）。两个脚本都内置了**行尾自愈**：检测到 CRLF 会自动修正并重新执行，因此无需手工处理。
> 建议统一用 `bash 脚本名.sh` 调用，不依赖可执行位与 shebang。

**第 2 步：导出基线（只读源库）**

```bash
bash export-baseline.sh <源库主机> <端口> <账号> <源库名> ./out
# 例如：bash export-baseline.sh miaoyu.asia 51001 ba ba ./out
```

按提示输入源库密码（不回显）。产出两个文件：

- `out/01-schema.sql`：全部表结构
- `out/02-flyway-history.sql`：`flyway_schema_history` 的迁移记录

**第 3 步：导入新库**

```bash
bash import-baseline.sh ./out/01-schema.sql ./out/02-flyway-history.sql ba-prod <新库用户名> 127.0.0.1 51001
```

按提示输入新库密码。脚本会：拒绝非空目标库 → 创建库 → 导入结构 → 导入迁移历史 → 打印表数量与 Flyway 最高版本。

**第 4 步：清理临时文件**

```bash
rm -rf ./out
```

### 4.2 方式二：Windows 本机导出 + 上传

适用于服务器无法访问源库、但本机能访问的情况。本机需要 `mysqldump`。

```powershell
cd BarcBackend\db\baseline
.\export-baseline.ps1 -Server <源库主机> -Port <端口> -User <账号> -Database <库名> -OutputDir .\out
```

然后把 `out` 下两个文件传到服务器，按方式一的第 3 步导入。

> 若本机没有 `mysqldump`（脚本会自检并提示），请改用方式一，或先安装 MySQL 客户端。

### 4.3 两个文件各自的作用

| 文件 | 内容 | 为什么必须 |
|---|---|---|
| `01-schema.sql` | 全部表结构（`--no-data`，不含业务数据） | 建出与最新版本一致的结构 |
| `02-flyway-history.sql` | `flyway_schema_history` 的记录 | 让 Flyway 认定"已是最新"，跳过全部历史迁移 |

**缺少第二个文件会导致 Flyway 从头重放 V1~V11**，从而撞上第二章列出的失败点。

### 4.4 验证

启动后端，日志应出现：

```
Current version of schema `ba-prod`: 11
Schema `ba-prod` is up to date. No migration necessary.
```

只要出现 `No migration necessary`（而不是 `Migrating`），即说明基线正确。

### 4.5 回滚

目标库只可能是新建的空库，导入有误时直接 `DROP DATABASE` 后重新导入即可；源库全程只读，不受影响。

### 4.6 常见报错与处理

| 报错 | 原因 | 处理 |
|---|---|---|
| `bad interpreter: /usr/bin/env bash^M` | 脚本带 Windows CRLF 行尾 | 脚本会自动修正；若仍失败，改用 `bash 脚本名.sh` 调用 |
| `mysqldump: command not found` | 服务器未装 MySQL 客户端 | `yum install mysql` / `apt install mysql-client`，或改用 Windows 方式二 |
| `Access denied for user ... (using password: YES)` | 密码错误或账号无权访问该库 | 确认账号密码；导出账号只需 SELECT 权限 |
| `Unknown database 'xxx'` | 源库名写错 | 核对源库名 |
| 导入时 `Table 'xxx' already exists` | 目标库非空 | 脚本本会拒绝非空库；如手工导入导致，清空目标库后重来 |
| 启动时 `Detected failed migration` | `flyway_schema_history` 中存在 `success = 0` | 用第六章 SQL 查出失败记录，人工处理后重试 |
| 启动时 `Schema ... is up to date` 未出现，反而大量 `Migrating` | `02-flyway-history.sql` 未导入 | 补导入该文件，或清空目标库后重新完整导入 |

### 4.7 生产库必需的基础配置数据

用基线脚本初始化出的新库**只有表结构、没有数据**（`--no-data` 刻意排除，避免开发数据进入生产）。因此需要按下表准备：

| 表 | 是否需要 | 说明 |
|---|---|---|
| `category` | **必需** | 作品分类。**全项目仅有 `@Select`，没有任何管理端增删改入口**，只能由数据库直接写入；缺失会导致上传作品无法选择分类、按分类浏览作品为空 |
| `festival` | 可选 | 管理端「系统管理 → 节日管理」可自行创建；V10 的固定种子 ID 未被任何代码引用，不导入无影响 |
| `feedback_type` / `feedback_option` | **不需要** | 已废弃（见 `AGENTS.md` 第六章）。反馈分类由后端 `FeedbackTypeEnum` 与前端 `src/utils/feedbackType.ts` 本地映射驱动，两个前端均不调用 `/feedback/all_types` 与 `/feedback/options_by_type` |
| `feedback_work` | **不需要** | 已废弃。作品投诉已统一走通用 `feedback` 表（`type = WORK`） |
| `school` / `club` / `student` / `notice` / `background_image` | 可选 | 管理端均有增删改入口，可自行创建 |

> **`category` 的数据来源**：从既有环境按表导出**数据**（不含结构）后导入新库：
>
> ```bash
> mysqldump -h <源主机> -P <端口> -u <账号> -p --no-create-info <源库> category > category-data.sql
> mysql -h 127.0.0.1 -P 51001 -u <生产账号> -p ba-prod < category-data.sql
> ```
>
> ⚠️ 只导 `category` 这一张配置表，**不要整库导出**，否则会把作品、评论、用户等业务数据一并带进生产。

## 五、路径 B：重编号重构迁移链（长期治理，暂缓）

> 目标：让 Flyway 自己就能从空库建库，彻底摆脱对 baseline 脚本的依赖。
> 现状评估：**方向正确，但不是低成本改动**，执行前必须满足下列全部前提。

### 5.1 必须处理的问题

1. **执行顺序**：Flyway 先于 `schema.sql`，因此新 V1 必须独立建出全部基础表。
2. **基线内容必须精确**：新 V1 必须等于"V1 执行前的结构"，即排除 V6 的 `work.content_updated_at`、V9 的 `background_image.time_period/festival`，否则顺延后的迁移会重复加列失败（MySQL 8 不支持 `IF NOT EXISTS`）。
3. **弃用复数表**：原 V1 的第一句就 `ALTER TABLE schools`，新库必须存在 `schools`/`students`。可选做法是让基线创建这两张僵尸表，再新增一条迁移 `DROP TABLE IF EXISTS` 清理。
4. **已发布迁移不可变**：改名/改版本号会破坏 `flyway_schema_history` 的 `version`/`script`/`checksum` 对应关系，所有现存库（开发库是唯一有数据的库）都必须做 history 手术，且需先备份。
5. **退役 `schema.sql`**：否则双份结构定义会继续漂移。

### 5.2 前置条件与风险控制

- 必须有一个可反复演练的**临时空库**，先在它上面验证整条新链能跑通；
- 必须完整备份开发库，并**单独备份 `flyway_schema_history`**；
- 手术方式二选一：以 `out-of-order` 让 Flyway 补执行新 V1；或 `flyway repair` 对齐 checksum 后手工补记录；
- 准备回滚：恢复 history 备份 + 还原全部迁移文件。

### 5.3 结论

完成后确实是**长久之计**（Flyway 成为唯一结构来源，后续只需追加迁移），但收益与路径 A 接近，风险显著更高。建议在具备演练环境后单独排期，**不要与上线同批执行**。

## 六、巡检：确认环境表结构完整

`schema.sql` 退役后，下面这些检查更有意义——表数量异常就说明结构与基线不一致：

```sql
SELECT COUNT(*) AS table_count
FROM information_schema.TABLES
WHERE TABLE_SCHEMA = '你的库名';

SELECT version, description, success, installed_on
FROM flyway_schema_history
ORDER BY installed_rank;
```

`success = 0` 的记录会使 Flyway 校验永久失败，必须处理。

**本项目实测基线导入后的预期值**：表数量 `36`、Flyway 最高版本 `11`、失败记录 `0`。

> 36 张的构成：`schema.sql` 的 30 张（退役前由它创建，现由基线脚本提供）+ Flyway 独有的 2 张（`cos_garbage_key`、`user_ban_record`）+ `flyway_schema_history` 1 张 + 历史遗留的 3 张弃用复数表（`schools`、`school_clubs`、`students`）。
> 那 3 张弃用表已无代码引用（mapper 全部使用单数 `student`/`school`/`club`），保留不影响功能。
